# 系统架构说明

核电工程隐患智能识别与定级系统（Demo）—— 前后端分层、目录结构与代码规范说明。

## 1. 总体架构

```
┌─────────────────────────── 浏览器 ───────────────────────────┐
│  React 19 + TypeScript + Vite                                │
│  ┌──────────┐ ┌──────────────┐ ┌──────────────────────────┐  │
│  │  pages/  │→│  components/ │ │  api/ 客户端（按领域）      │  │
│  │  页面     │ │  展示组件     │ │  client·model·analysis    │  │
│  │          │ │              │ │  ·rules·knowledge         │  │
│  └──────────┘ └──────────────┘ └───────────┬──────────────┘  │
│            lib/（纯函数：storage/theme/      │ fetch /api/*    │
│            imageUtils/rules/radialGraph）    ▼                │
└─────────────────────────────────────────┼────────────────────┘
                                          │ (Vite dev 代理 :5175 → :3001)
┌─────────────────────────────────────────▼────────────────────┐
│  Node.js + Express（tsx 运行 TS 源码）                        │
│  server/index.ts（入口：.env 加载 + 监听）                     │
│  server/http/（路由层：参数解析/响应编排，无业务逻辑）            │
│  ┌──────────┬──────────────┬───────────┬─────────────────┐   │
│  │ model    │ knowledge    │ rules     │ analysis        │   │
│  │ .routes  │ .routes      │ .routes   │ .routes         │   │
│  └──────────┴──────────────┴───────────┴─────────────────┘   │
│  server/services/（业务服务：model-config 运行期配置）          │
│  server/agent/runtime.ts（run/step/LLM call/context/cache/trace）│
│  server/agent/workflows/hazard-analysis.ts（显式状态工作流）    │
│  server/pipeline.ts（旧接口兼容门面）                           │
│  server/providers/（多模态 Provider：openai-compatible）│
│  server/retrieval/（知识检索）、server/rules/（规则解析与库）     │
│  server/grading/（A/B/C/D 定级规则）   │
│  server/lib/（env 加载 / Zod schema / Prompt 构建）            │
└─────────────────────────────────────────┼────────────────────┘
                                          │
                        shared/（前后端共用类型与纯函数）
                        types.ts · grading-meta.ts · report.ts
```

**请求链路示例**（图片隐患识别）：

```
页面（Workbench） → api/agent.analyzeImageStream() → POST /api/agent/runs/stream
  → http/agent.routes（multer 接收图片、SSE 事件输出）
  → AgentRuntime（run/step/tool/cache/trace）
  → hazard-analysis workflow（Preflight → Vision → RAG → Rules → Context → Reasoning → Validation → Result）
  → result.completed + run.completed → 页面渲染

旧客户端继续使用 `/api/analyze`，该接口内部调用同一个 AgentRuntime 后一次性返回最终 `AnalysisResult`。
```

## 2. 目录结构

### 2.1 后端 `server/`

| 目录 / 文件 | 职责 | 依赖方向 |
| --- | --- | --- |
| `index.ts` | 入口壳：加载 `.env`、组装应用、监听端口 | 只依赖 http/app |
| `http/app.ts` | Express 应用组装：中间件、注册各路由、生产静态托管、404 兜底 | 依赖各 routes |
| `http/*.routes.ts` | 路由层：HTTP 参数解析、状态码与响应体编排；**不写业务逻辑** | 依赖 services / 领域模块 |
| `http/helpers.ts` | `sendJson` / `sendError` / `asyncHandler` 统一响应工具 | 无 |
| `services/model-config.ts` | 运行期模型配置存储（`.runtime-model.json` 持久化 + 环境变量合并） | node:fs |
| `agent/runtime.ts` | Run 生命周期、真实事件、LLM Call/Tool 观测、Token 聚合、缓存指标、Session 摘要、结果 meta | workflow / providers / repositories |
| `agent/workflows/hazard-analysis.ts` | 显式图片分析 workflow 与节点跳转/降级 | context / retrieval / rules / grading |
| `agent/observability/token-usage-store.ts` | 调用级 Token Ledger；Run / Session / Conversation 聚合 | shared/token-usage、providers/types |
| `agent/observability/context-observability-store.ts` | Provider request 级不可变 Context Snapshot、Agent/Turn/LLM Step、Diff、Prune/Compression 与 actual Usage Ledger | shared/context-observability、providers/types |
| `pipeline.ts` | 旧调用兼容门面，内部创建 AgentRuntime | agent/runtime |
| `providers/` | 多模态 Provider 抽象（`types.ts`）与实现（`openai-compatible.ts`），`index.ts` 为工厂 `resolveProvider()` | services/model-config |
| `retrieval/index.ts` / `service.ts` | keyword/category recall + 绝对分数 + 来源多样性 + 版本化 TTL cache | shared/types、data/*.json |
| `rules/` | 判定规则解析器（`parser.ts`：TXT/CSV 两遍解析）与规则库持久化（`index.ts` → `.rules-imported.json`） | shared/types |
| `grading/risk-grading.ts` | A/B/C/D 定级权威规则：风险矩阵、定级理由、模型输出护栏 | shared |
| `lib/` | `env.ts`、Zod Schema、版本化 Prompt；Context 组装位于 `agent/context/` | zod |
| `data/` | 标准文档、历史案例、演示规则样本（JSON/TXT/CSV） | — |

**分层原则**：

- `http/` 只做「请求进来 → 调业务 → 响应出去」，错误统一走 `sendError`（`{ error, code? }`）；
- 业务模块之间**单向依赖**：HTTP → Agent Runtime → Workflow → providers/retrieval/rules/grading → shared，不反向引用 HTTP 层；
- 所有共享数据从进程启动时加载一次（检索索引、规则库、JSON 数据）。

### 2.2 前端 `web/`

| 目录 / 文件 | 职责 |
| --- | --- |
| `main.tsx` / `App.tsx` | 入口与外壳：hash 路由分发、主题、顶栏模式状态 |
| `pages/` | 页面级组件（Workbench 工作台、Records 记录、Rules 规则库、Knowledge 知识库、Graph 图谱、Discover 发现、Prevent 防控、Settings 设置） |
| `components/` | 展示组件（ImagePanel、ImageAnnotator、HazardCard、EvidenceDrawer、TopBar、AppSidebar、icons 等） |
| `api/` | **API 客户端（按领域拆分）**：`client.ts`（fetch 封装 + ApiError）、`model.ts`、`analysis.ts`、`rules.ts`、`knowledge.ts` |
| `lib/` | 纯前端逻辑（constants 常量、theme 主题、storage localStorage、ledger 台账、imageUtils 图片处理、sampleScenes 演示场景、discovery 摄像头/机器人、radialGraph 图谱布局、useHashRoute 路由 hook） |
| `styles.css` | 全局设计系统（CSS 变量主题） |

**页面 → 数据流向**：`pages` 只允许通过 `api/` 访问后端；`lib/` 提供纯函数与本地存储，禁止页面直接拼 `fetch`。

### 2.3 共享 `shared/`

| 文件 | 内容 |
| --- | --- |
| `types.ts` | 领域类型：`AnalysisResult` / `Hazard` / `StandardClause` / `HistoricalCase` / `GradingRule` 等 |
| `agent-protocol.ts` | Agent run/status/event/trace 与前端状态的共享协议 |
| `token-usage.ts` | LLM Call、Run、Session、Conversation 的统一 Token Usage 数据结构 |
| `context-observability.ts` | 六类 Context Item、Snapshot、Agent/Turn/LLM Step、Diff、事件与 Statistics Model |
| `grading-meta.ts` | A/B/C/D 分级定义（标签、规则、配色） |
| `report.ts` | 报告 HTML 渲染（纯函数，服务端 /api/export 与前端共用） |

## 3. 数据与状态

| 数据 | 存储位置 | 说明 |
| --- | --- | --- |
| 标准 / 案例 / 企业文件 | `server/data/*.json` | 后端内存索引，启动时加载；前端经 `/api/standards`、`/api/cases` 读取 |
| 判定规则（导入） | `.rules-imported.json`（gitignore） | 后端按编码去重持久化；前端经 `/api/rules*` 读写 |
| 模型运行期配置 | `.runtime-model.json`（gitignore） | 模型配置页面写入，优先级：运行期 > 环境变量；未配置真实模型时返回错误 |
| 分析结果 / 记录 / 台账 / 主题 | localStorage（`hazard.*.v1` 键） | 前端本地持久化 |
| Run / Event / Session 摘要 / Context Cache | 后端有界进程内存储 | Demo 首期实现；生产迁移到数据库 / Redis / 对象存储 |
| LLM Call Token Ledger | 后端有界进程内存储 | Provider 实际 usage 归一化后逐调用保存；聚合值不另设事实副本 |

## 4. 代码规范

### 4.1 目录与文件

- 目录名、文件名一律小写 + kebab-case（`model-config.ts`、`risk-grading.ts`），组件文件例外可用语义名（`HazardCard.tsx`）；
- 服务端 ESM：相对导入必须带 `.js` 扩展名（`import x from '../lib/env.js'`）；
- 前端模块化导入不带扩展名。

### 4.2 命名

| 类别 | 规范 | 示例 |
| --- | --- | --- |
| 文件 | kebab-case / PascalCase（组件） | `risk-grading.ts`、`HazardCard.tsx` |
| 函数/变量 | camelCase | `runAnalysis`、`mimeOf` |
| 组件 | PascalCase | `ImageUploader` |
| 常量 | UPPER_SNAKE_CASE | `ALLOWED_MIME`、`RUNTIME_FILE` |
| 类型/接口 | PascalCase + 语义后缀 | `AnalysisResult`、`MultimodalModelProvider` |

### 4.3 注释

- 每个模块顶部必须有 JSDoc 首行注释，说明职责与依赖方向（参考 `server/http/*.routes.ts`）；
- 路由模块在头部列出全部端点与参数；
- 中文注释优先，公共导出函数补充一行用途说明。

### 4.4 分层约定

- **路由层不写业务逻辑**：校验参数、调服务、返回响应；复杂判断下沉到 services / 领域模块；
- **业务层不感知 HTTP**：不 import express 类型，错误通过抛错 + 路由层 `sendError` 或错误码（如 `MODEL_ERROR` → 502）转换；
- **错误响应统一**：`{ error: string, code?: string }`，成功响应按资源定义（`{ ok, data, ... }` 或直接 payload）；
- API 客户端方法命名与端点对应：`fetchXxx`（GET）/ `xxxXxx`（POST 动作）。

### 4.5 容错

- 大模型输出必须经 `lib/schema.ts` 的 Zod 校验（`safeParseModelJson`）才能进入业务数据；
- 视觉模型失败是终止错误；推理模型失败走可观测的确定性保守降级并强制人工复核；旧 JSON 接口将终止错误映射为稳定 HTTP 错误码；
- 本地存储（JSON 落盘 / localStorage）读取失败一律降级为默认值，不阻塞启动。
